# 前端设计与工程规范

## 1. 产品与职责

前端是 Evidence-first Interview Studio，不是通用聊天窗口。任何主流程都应优先回答：问题来自项目哪里、当前进度如何、评价后下一步怎么做。

- 前端展示后端提供的项目事实、问题、评价、画像提示和追问方向。
- 前端不得自行评分、推断 Analyzer 类型、重建证据关系或更新候选人画像。
- Tauri 能力通过独立调用边界接入；浏览器模式必须具有可理解的降级反馈。
- 应用级设置不绑定项目；API Key 只提交给后端，绝不写入 localStorage、日志或公开 payload。

## 2. 前端代码边界

当前最小边界保持为：

```text
React View / Interaction
    ↓
UI mapping and local view state
    ↓
frontend/src/api.js
    ↓
OpenAPI-defined backend
```

- 所有 HTTP 请求集中在 `frontend/src/api.js`；组件不得直接散落 `fetch`。
- API 数据进入 UI 前可做显示归一化，但不得改变业务语义或计算评分。
- 文件读取与上传描述构建放在 `upload.js`；编辑器纯文本行为放在 `composer.js`。
- 拆分组件以“独立状态或可独立测试的交互”为依据，不为一次性片段创建抽象。
- 引入状态管理、请求缓存或路由库前，必须先证明现有 React 状态边界不足。

## 3. API 与错误处理

- 前端只依赖 `docs/api/openapi.json` 中声明的字段和状态码。
- 请求失败对象至少保留 `status`、`code`、`retryable`、`requestId` 和后端 details。
- UI 根据 `code` 决定恢复动作；`error` 文本用于展示，不用于业务分支。
- 不自动重试回答提交、配置保存、档案删除等写操作。
- 可重试读取可以提供显式“重试”操作；若未来自动重试，必须限制次数并允许取消。
- 请求进行中锁定对应写操作，但不应冻结与请求无关的整个应用。

## 4. 状态模型

每个异步区域按适用范围覆盖以下状态：

| 状态 | 必须表现 |
| --- | --- |
| 初始 | 告诉用户可以做什么，不伪造已有数据 |
| 加载 | 说明正在处理的对象或阶段，写操作禁用重复提交 |
| 空 | 解释为什么为空，并提供下一步入口 |
| 成功 | 更新真实数据；重要写操作给出可读确认 |
| 失败 | 保留上下文和输入，展示可读消息与适用的恢复动作 |
| 禁用 | 视觉、语义和键盘行为一致，不只降低透明度 |

项目上传必须显示读取文件、上传项目、分析项目、建立会话四个阶段。分析状态不得用无限旋转动画掩盖失败；收到 `FAILED` 或 422 后保留服务端错误。

## 5. 设计系统

### 语义 Token

颜色使用 `styles.css` 的语义变量，不在新组件中重复硬编码同义色：

- `--paper`：应用背景。
- `--surface`、`--surface-soft`：主/次表面。
- `--line`：少量必要的真实边界，不作为默认布局工具。
- `--ink`、`--ink-soft`、`--muted`：三级文字。
- `--amber`、`--amber-soft`：主操作、当前状态和项目证据强调。
- `--green`：成功和在线；`--red`：错误和风险。

新增 token 必须按语义命名，不能按具体页面或临时颜色命名。正文优先系统中文字体回退；等宽内容使用 `DM Mono` 或系统等宽字体。远程字体加载失败不得影响可用性。

### 间距与形态

- 基础间距采用 4px 倍数；常用组件间距优先 8、12、16、24、32px。
- 交互控件最小可点击区域为 32×32px，移动端主要操作建议至少 40px 高。
- 同层容器优先用一致的留白、圆角和明度层级分组；边框不是卡片的默认配置。
- 浮层可以使用克制的柔和阴影表达覆盖关系；普通内容区不同时叠加边框、阴影和背景反差。
- 主操作每个局部区域最多一个；危险操作不得使用主强调色伪装。

### 边界、分隔与表格感控制

界面默认采用“少线层级”：先用留白、排版、缩进、背景明度和局部分组建立关系，只有这些方式不足以表达真实边界时才使用线。

一条可见横线或竖线必须至少承担以下一种明确语义：

1. 可拖拽、可聚焦的分栏控制边界。
2. 独立滚动区域、窗口或抽屉的真实边界。
3. 代码、时间线或高密度数据表中需要持续对齐的数据基准。
4. 焦点、错误或选中状态的临时反馈。

不满足上述条件的线应删除，并按顺序改用：`16–32px` 间距 → 标题/字重层级 → 缩进或分组 → `--surface-soft` 明度差 → 局部圆角表面。

具体约束：

- 不在每个标题、卡片、列表行或表单行下面画满宽横线；连续信息通过段落间距和分组标题组织。
- 不用竖线把普通内容切成类似表格的单元格；并列卡片优先使用 gutter 和表面明度区分。
- 一个组件最多使用一层常驻外边界；有外框时，内部默认不用重复分隔线。
- 同一屏幕不得同时用卡片外框、行分隔线和列分隔线表达同一组关系。
- 设置项、指标和属性列表默认采用无网格行组；只有用户需要跨行、跨列精确比较时才使用真正的数据表格。
- 数据表也优先保留行分隔或斑马底色二选一；除非列对齐无法辨认，不同时绘制完整横纵网格。
- 树结构使用缩进、展开图标和节点状态表达层级，避免贯穿整区的装饰性连接线。
- 可拖拽分栏的可见线保持 `1px` 弱对比；命中区域可扩至 `8–12px`，仅在 hover、拖拽或键盘聚焦时增强颜色。
- 相邻父子容器不得形成“双线”：父容器已有边界时，子容器贴边位置不再重复画线。
- 横线不应从窗口一侧连续贯穿到另一侧，除非它确实表示窗口级区域边界。

需要强调分组时，优先采用“内容岛”而不是“单元格”：一组信息共享一个柔和表面与内部留白，组与组之间留出明显间距。视觉上缩小或眯眼检查时，如果页面首先呈现为行列网格，而不是主问题、证据和操作层级，则视为未通过设计验收。

### 响应式断点

- `>1180px`：完整桌面工作台，可并列侧栏、主区和证据区。
- `921–1180px`：收窄侧栏与证据区，保持主问题可读。
- `621–920px`：隐藏侧栏，证据作为主区后的可展开区域。
- `<=620px`：单列移动布局，主操作全宽，次要头部操作可折叠但不能丢失关键能力。

不得只按截图宽度通过；长项目名、长错误、空证据和多条评价也必须保持可读。

## 6. 组件与交互约定

- 原生语义元素优先：操作使用 `button`，表单字段具有可关联 label，状态消息使用适当的 `role=status` 或 `aria-live`。
- 图标按钮必须有可读 `aria-label`；图标不能作为唯一错误或成功信号。
- 菜单支持 Escape 关闭和点击外部关闭；打开后键盘焦点不得丢失。
- 抽屉打开/关闭状态通过 `aria-expanded`、`aria-controls`、`aria-hidden` 等适用属性同步。
- Enter 提交与换行行为必须在编辑器附近说明；提交期间保持内容可见。
- 删除、覆盖项目等难恢复操作需要明确目标，并在适用时二次确认。

## 7. 无障碍

- 所有键盘可操作元素具有可见 `:focus-visible` 样式。
- 正文与背景、重要控件与背景应满足 WCAG AA 对比度；不能只用颜色区分状态。
- 尊重 `prefers-reduced-motion`，关闭非必要动画和过渡。
- 错误反馈靠近相关字段，并通过辅助技术可感知。
- DOM 顺序保持阅读顺序；视觉重排不得制造错误的键盘顺序。
- Design QA 至少检查键盘导航、200% 缩放、窄屏和无鼠标提交主流程。

## 8. 文案与本地化

- 面向用户的主文案使用中文，代码、路径、枚举和产品专名保持原文。
- 错误文案说明发生了什么和下一步，不使用“未知错误”作为可恢复场景的最终反馈。
- 不在 UI 硬编码 Analyzer 能力承诺；展示后端 `analyzer_id`、状态和证据事实。
- 日期、时间、分数和文件大小通过统一格式化函数输出；新增多语言前先集中用户文案，避免散落拼接。

## 9. 测试与视觉验收

- `api.test.mjs` 验证请求路径、方法、body 和结构化错误。
- 纯函数测试覆盖上传路径、容量、二进制过滤和编辑器文本行为。
- 交互测试覆盖启动、上传、回答提交、设置保存、失败恢复和桌面能力降级。
- 响应式或视觉层级变化必须更新 Design QA 截图与结论。
- Design QA 必须执行“线条审计”：标记所有满宽横线、满高竖线和重复边框；每一条都要能说明其真实边界或交互语义，否则移除。
- 桌面截图若呈现明显表格网格感，或同一信息组同时出现外框、横线和竖线，应判为需要整改，而不是视觉偏好问题。
- `npm test` 和 `npm run build` 是前端最低门禁；Sites 交付还必须通过 `npm run test:sites`。
