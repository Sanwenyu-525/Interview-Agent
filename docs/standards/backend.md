# 后端设计与工程规范

## 1. 分层与依赖方向

后端保持以下单向依赖：

```text
HTTP / Server
    ↓
Application Service
    ↓
Domain Review + Project Intelligence
    ↓
Repository / Session Store / Profile Store / LLM Adapter
```

- HTTP 层只解析协议、映射状态码和序列化响应，不生成问题、不计算评分。
- Application Service 编排上传、分析、会话和持久化，不包含语言专属解析规则。
- Analyzer 只产生项目事实和证据；Review Policy 只决定评审主题与追问方向。
- LLM、SQLite、文件系统和未来框架都通过现有边界接入，不散落到模型或 UI。
- Tauri Rust 壳只负责窗口和本地桌面能力，不承载领域逻辑。

## 2. 模型规则

- 领域状态使用明确的数据类、枚举或协议，必须能够转为 JSON-safe 数据。
- `UniversalProjectModel` 的组件、关系、流程、主题必须通过真实 `evidence_ids` 回指证据。
- 路径统一为相对 artifact root 的 POSIX 路径；不得持久化 `Path`、AST、连接或运行时对象。
- 通用模型不得出现 Java、Spring、React 或某个行业专属的必填字段。
- 兼容模型只能位于显式转换边界，不能形成双向写入或两套独立事实源。

## 3. HTTP 契约

`docs/api/openapi.json` 是路径、方法、字段和状态码的唯一事实源。实现必须满足：

- 请求与响应为 UTF-8 JSON；不在同一路径混用 JSON、multipart 和文件流。
- 成功状态码保持稳定：创建使用 `201`，读取/更新使用 `200`，预检使用 `204`。
- 路径 ID 和 body ID 必须归一化并校验；布尔值不得被当作整数 ID。
- 未在 OpenAPI 中声明的响应字段只能作为向后兼容扩展，客户端不得因此承担业务计算。
- `schema_version` 是持久化 payload 版本，不等于 HTTP API 版本。

当前 API 为本地未加版本前缀的 v1 契约。破坏性变更必须提供迁移窗口或新版本路径，不得静默改变现有字段语义。

## 4. 统一错误协议

所有非 2xx JSON 响应至少包含：

```json
{
  "error": "可直接展示或记录的消息",
  "code": "stable_machine_code",
  "retryable": false,
  "request_id": "关联本次请求的标识"
}
```

- `error` 为旧客户端兼容字段；新客户端根据 `code` 分支，不解析消息文本。
- `retryable=true` 只表示在状态刷新或上游恢复后重试可能成功，不代表前端必须自动重试。
- `request_id` 同时写入 `X-Request-ID` 响应头，用于问题定位。
- 400 表示请求无效，404 表示资源不存在，409 表示版本冲突，422 表示项目内容无法完成分析，502 表示 LLM 上游失败。
- 远程部署时不得向客户端返回堆栈、密钥、数据库路径或上游原始凭据。

## 5. 校验与资源限制

- 在系统边界校验类型、必填字段、枚举、空字符串、数值范围和路径安全。
- Folder/ZIP 输入必须拒绝绝对路径、目录穿越、链接、重复路径和文件/目录冲突。
- 默认上传限制保持前后端一致：10000 文件、单文件 10 MiB、总文本/解压大小 100 MiB。
- 服务端限制是最终边界；前端预校验只用于快速反馈。
- Analyzer 无法确认的事实保持缺失或 unresolved，不得猜测成确定事实。

## 6. 一致性、并发与幂等

- 会话和面试者画像更新必须使用现有版本/CAS 机制，冲突返回 409。
- 回答提交不是通用幂等操作；前端在请求未完成时必须阻止同一界面的重复提交。
- 同一 `project_id` 的重复上传表示替换该项目来源，必须保持现有 staging/restore 的原子性。
- 涉及两个存储的操作必须定义失败恢复顺序，并测试原始错误与回滚错误都可追踪。

## 7. 持久化与迁移

- 每种持久化 JSON payload 都有独立 `schema_version`。
- 读取支持的旧版本时显式迁移；遇到未知版本、非法 JSON 或对象 ID 不匹配时必须失败。
- 写入只产生当前版本，不继续生成旧格式。
- 数据库迁移必须可重复执行，并在临时数据库上验证重启恢复。
- API Key 只存于后端设置存储；公共 payload 只能返回 `api_key_set`。

## 8. 安全与运行边界

当前服务是单用户本地桌面 MVP：

- 默认且正式支持的监听地址只有 `127.0.0.1`；不得将当前无认证服务绑定到公网或局域网接口。
- CORS 只回显允许的本地/Tauri 开发来源；未知网页来源的预检请求返回 403，不允许使用通配来源。
- 如需远程部署，必须先增加身份认证、资源授权、严格 CORS、TLS、限流、审计日志、密钥托管和数据保留策略。
- 不记录 API Key、面试者完整回答、源文件全文或 LLM Authorization header。
- ZIP `source_path` 只能用于服务进程可访问的本地文件；不得演变为任意 URL 下载器。

## 9. 可观测性与健康检查

- `GET /health` 只表示进程可接收请求，不承诺数据库或 LLM 上游健康。
- 每个响应提供 `X-Request-ID`；后续增加日志时必须使用同一 ID 关联请求。
- 用户可恢复错误使用明确状态码与稳定错误码，不通过日志代替响应反馈。
- 远程 LLM 调用必须有正数超时；是否重试由调用场景明确决定，默认不在回答提交中静默重试。
- 若未来把分析改为后台任务，状态必须继续使用 `CREATED → SOURCE_READY → SCANNING → ANALYZING → READY|FAILED`，并定义轮询间隔和取消语义。

## 10. 测试要求

- 模型：序列化往返、证据引用、未知版本和非法字段。
- Analyzer：支持判断、确定性选择、来源定位、解析失败与不猜测行为。
- Service：成功链路、回滚、并发冲突、面试者隔离和重启恢复。
- HTTP：状态码、统一错误结构、CORS 预检、密钥脱敏和 OpenAPI 操作覆盖。
- 修复缺陷时先增加可复现测试；新增端点必须同时进入 `PUBLIC_API_OPERATIONS` 和 OpenAPI。
